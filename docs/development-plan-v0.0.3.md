## 2. 版本目标

`v0.0.3` 不扩大核心业务边界，重点解决当前使用过程中的三类问题：

1. 高频操作步骤偏重，尤其是维护时间设置仍依赖手动输入。
2. 用户完成操作后需要手动刷新，状态反馈滞后。
3. 管理员处理链路不够直达，待办入口分散。

本版本目标如下：

1. 降低管理员设置维护时间的输入成本。
2. 对同课题重复预约同一时段给出明确业务反馈。
3. 将预约开放窗口从“按时刻滚动”调整为“按自然日开放”。
4. 让关键操作后的数据刷新默认自动完成。
5. 提升管理员在周历和后台首页中的处理效率。
6. 降低周历长按选择的误触概率。
7. 收敛时段治理模型，取消受限时段，仅保留维护规则，使实现与管理流程更一致。
8. 收敛管理入口，统一“注册用户/课题待审”处理路径，并让用户管理页只展示已通过用户。
9. 将规则复审合并到取消待审处理链路，并将使用统计收纳到系统设置下。
10. 管理员在周历点击单元格时按状态直达预约信息、审核确认或维护信息；空闲可操作格再进入维护创建流程。
11. 通过服务端硬校验和关键写入互斥，修补维护模式、法务版本、并发占用与候补转正的边界风险。

## 3. 版本范围

### 3.1 本次纳入

1. 维护时间录入改为轮盘式选择。
2. 同课题重复预约同一时段时返回专门提醒。
3. 预约开放窗口改为按自然日计算，支持预约到第 7 个自然日全天。
4. 用户和管理员完成关键操作后自动刷新当前页面数据。
5. 管理员周历显示“课题简称 + 预约人姓名”。
6. 长按逻辑调整为“滑动时不触发长按”。
7. 多选模式下不可跨周，并屏蔽“上周 / 下周”按钮。
8. 管理首页改造为待办卡片直达处理页为主入口。
9. 下线受限时段管理与相关云函数，收拢为单一维护模型。
10. 修复维护逻辑中的取消范围、并发保护、权限边界、兼容数据与整点约束。
11. 用户管理页只显示已通过用户。
12. 将“注册审核”和“课题申请审核”合并为单一 dashboard 入口“注册用户/课题待审”，不再保留两个独立管理功能入口。
13. 将规则复审并入“取消待审”入口，不再保留独立规则复审入口。
14. 将使用统计功能并入系统设置，不再保留独立“统计”入口。
15. 管理员在周历点击单元格时按状态分流：已预约进入预约信息、待确认进入审核确认、维护进入维护信息、空闲格进入维护创建。

### 3.2 本次不纳入

1. 不为普通占用格新增完整详情页或复杂详情弹层。
2. 不引入独立于课题之外的新“组”模型。
3. 不开放更多组内共享信息展示能力。
4. 不修改“最小预约单位 1 小时、整点提交”的基础规则。

## 4. 关键业务定义

### 4.1 课题与组的关系

本版本中，“组”仅作为业务理解辅助，不引入新数据模型。

执行口径：

1. 当前系统中的“课题”继续作为唯一归属单位。
2. “同组”在本版本中等价于“同课题”。
3. 组内共享信息本版本不扩展到成员列表、统计信息或历史记录展示。
4. 组概念仅落在预约冲突规则层，不额外开放新的展示权限。

### 4.2 管理员与普通用户展示差异

周历相关信息继续执行最小必要展示原则：

1. 普通用户只看到公开可展示的占用状态与课题简称。
2. 管理员可在周历格中看到“课题简称 + 预约人姓名”。
3. 普通用户不可见姓名、备注、审核意见等敏感信息。

### 4.3 用户管理展示范围

本版本中，用户管理页的职责收敛为“管理已生效账号”。

执行口径：

1. 用户管理页只显示已通过注册审核的用户。
2. `registrationStatus != approved` 的记录不在用户管理页展示。
3. 已通过但账号被暂停的用户仍属于用户管理页管理范围。
4. 待审核用户和待审核课题不再通过“用户管理”入口处理。

### 4.4 注册与课题待审入口收敛

本版本中，不再区分“用户注册审核入口”和“课题申请审核入口”的首页入口层级。

执行口径：

1. 管理首页待办区使用单一入口“注册用户/课题待审”。
2. 该入口承接原“注册审核”和“课题申请审核”的处理职责。
3. 管理功能菜单中不再保留两个独立入口。
4. 统一入口页采用同页分两段结构：`用户待审` / `课题待审`。
5. 本版本不采用混排列表，也不要求管理员先从首页区分类型再进入。

### 4.5 取消待审与规则复审口径

本版本中，规则复审不再作为独立入口存在。

执行口径：

1. 规则复审并入“取消待审”处理链路。
2. 管理首页待办区只保留一个“取消待审”入口。
3. 后台菜单中不再保留独立“规则复审”入口或文案。
4. 统一入口页采用同页分两段结构：`取消待审` / `规则复审`。

### 4.6 使用统计入口口径

本版本中，使用统计不再作为独立一级功能入口存在。

执行口径：

1. 使用统计放入“系统设置”功能下。
2. 管理首页和管理菜单中不再单独暴露“统计”入口。
3. 系统设置页负责承接统计查看入口或统计展示内容。

## 5. 功能需求

### 5.1 维护时间录入优化

#### 5.1.1 现状

当前维护页通过手动输入 `startAt` 和 `endAt` 创建维护时段，操作路径偏重，且容易出现格式输入不一致的问题。

#### 5.1.2 目标

将维护时段录入改为轻量、结构化、低出错的选择流程。

#### 5.1.3 新交互

维护时间创建改为以下三个字段：

1. 日期
2. 开始小时
3. 时长

系统根据“开始小时 + 时长”自动计算结束时间。

默认值规则：

1. 默认日期为今天。
2. 默认开始时间为下一整点。
3. 默认时长为 1 小时。

#### 5.1.4 规则

1. 开始小时按整点选择。
2. 时长按小时递增。
3. 时长选择范围为 1-12 小时。
4. 最终提交给云函数的仍然是标准 `startAt` / `endAt` 时间。
5. 原有维护冲突确认逻辑保留：若维护时段覆盖已有预约，系统仍按既有规则取消冲突预约。

确认信息要求：

1. 创建维护前显示起止时间。
2. 显示本次维护总时长。
3. 显示受影响预约数量。
4. 明确提示“将取消未来有效预约”。

#### 5.1.5 实现影响

- 前端主要改造 `miniprogram/pages/admin/maintenance/`
- 云函数 `createMaintenance` 无需变更接口协议，优先保持兼容

### 5.2 同课题重复预约提醒

#### 5.2.1 目标

当同一课题成员在相同时段重复预约时，系统应返回明确业务提示，而不是仅返回通用占用冲突。

#### 5.2.2 规则

1. 用户提交预约时，系统检查目标时段内是否存在同课题的有效预约记录。
2. 若存在，则直接拦截本次预约。
3. 返回统一提示文案：

```text
该时段已被本课题预约
```

#### 5.2.3 边界

1. 本次仅返回统一提醒文案。
2. 本次不在普通用户侧展示具体成员姓名。
3. 本次不扩展为组内共享记录浏览能力。

#### 5.2.4 实现建议

1. 在 `createBookingV2` 中于通用冲突校验前增加同课题冲突判断。
2. 判断集合应与现有有效预约状态保持一致，避免出现业务口径不一致。

### 5.3 预约按自然日开放

#### 5.3.1 目标

解决当前“按时刻滚动 7 天开放”带来的边界问题，使预约窗口按自然日计算。

#### 5.3.2 新规则

1. 预约开放范围按自然日计算，而不是按当前时刻精确加 `7 * 24` 小时计算。
2. 用户在任意时刻可预约到“当前日期 + 7 个自然日”当天的全部可预约整点时段。
3. 示例：若当前是周四，则可预约到下周四全天的可预约时段。
4. 当前小时与过去时段仍然不可预约。
5. 预约最小单位、整点规则、多时段模型保持不变。
6. 多选仍限制在当前周视图内，不支持跨周连续选择。

#### 5.3.3 实现要求

1. 取消“只能预约到当前时刻后精确 7 天”的限制。
2. 取消“所有时段必须处于同一自然周”的限制。
3. 改为校验每个时段是否落在可预约日期窗口内。
4. 若预约单包含多个时段，则每个时段都必须分别满足新窗口规则。

### 5.4 多选不可跨周

#### 5.4.1 目标

避免用户在连续多选过程中切换周视图，导致选择上下文混乱或形成跨周多选。

#### 5.4.2 交互规则

1. 多选模式仅在当前周视图内生效。
2. 进入多选模式后，页面上的“上周 / 下周”按钮置为禁用状态。
3. 退出多选模式后，翻周按钮恢复可用。
4. 单格点击和普通浏览状态下，翻周按钮保持可用。
5. 用户点击禁用状态的翻周按钮时，提示“多选中不可切换周，请先退出选择”。

#### 5.4.3 业务边界

1. 按自然日开放预约不等于支持跨周多选。
2. 用户若要选择跨周时段，需要分别在不同周内单独提交。

### 5.5 操作后自动刷新

#### 5.5.1 目标

用户和管理员完成关键操作后，页面默认刷新到最新状态，减少手动刷新成本。

#### 5.5.2 原则

1. 所有关键操作统一执行自动刷新。
2. 优先刷新当前页数据。
3. 需要时同步刷新全局用户状态或待办统计。

#### 5.5.3 覆盖场景

包括但不限于：

1. 提交预约
2. 取消预约
3. 候补确认
4. 管理员审核预约
5. 管理员审核取消
6. 管理员审核注册
7. 管理员审核课题申请
8. 维护新增与删除
9. 用户状态处理

#### 5.5.4 页面要求

1. 成功提交后自动拉取最新列表或最新周历数据。
2. 刷新时尽量保留当前上下文，例如当前周、当前筛选和当前标签。
3. 不要求用户手动下拉刷新才能看到结果。
4. 成功反馈采用“成功 toast 后静默刷新”。
5. 自动刷新后保留当前周、当前筛选和当前标签，不强制恢复滚动位置。

### 5.6 受限时段下线

#### 5.6.1 目标

减少管理员时段治理负担，收敛为单一的维护模型，降低后台配置复杂度与规则歧义。

#### 5.6.2 调整方案

1. 管理后台不再提供“受限时段”创建、删除和列表管理入口。
2. 周历不再展示受限状态。
3. 预约审核来源收敛为系统规则触发，例如周末、非工作时间。
4. 不再保留“管理员手工设置一个可申请但需审核的窗口”能力。

#### 5.6.3 数据与兼容处理

1. 已存在的 `restricted_slots` 不再作为生效规则继续参与预约判断。
2. 相关云函数进入停用状态，不再由前端调用。
3. 后台入口、图例、提示文案和审核来源说明需要同步收口。
4. 当前项目仍处于测试阶段，无需额外设计历史受限数据展示或迁移页面。

#### 5.6.4 后台入口处理

1. 管理页中“受限时段”入口直接删除。
2. 不保留“已停用”占位入口。
3. 管理菜单仅保留 `维护 / 设置` 作为非待办入口。

### 5.7 周历交互边界

#### 5.7.1 本次不新增

1. 不为普通占用格新增完整详情页。
2. 不新增复杂的多层详情弹层。
3. 不改变当前周历主流程中“点击单格快速选择 / 长按进入连续选择”的结构定位。

#### 5.7.2 本次增强范围

1. 管理员周历增加预约人识别信息。
2. 多选模式增加跨周保护。

### 5.8 管理员周历显示预约人

#### 5.8.1 目标

让管理员在周历层直接识别预约人，减少进入详情页核对的频率。

#### 5.8.2 展示规则

管理员周历单元格展示格式为：

```text
课题简称 + 姓名
```

普通用户周历不显示姓名。

#### 5.8.3 权限要求

1. 必须在服务端确认管理员身份后返回姓名。
2. 公开周历接口不能直接无差别向所有用户暴露姓名字段。
3. 客户端不得以前端条件分支替代服务端权限判断。

#### 5.8.4 实现方向

可选方案：

1. 扩展周历数据接口，在管理员身份下附带姓名字段。
2. 或为管理员提供单独的数据路径，但仍复用当前周历页面结构。

优先选择改动最小、合规风险最低的实现方式。

### 5.9 管理员周历点击按状态分流

#### 5.9.1 目标

让管理员在周历上按单元格当前状态直接进入对应处理页面；只有空闲可操作格才进入维护创建流程。

#### 5.9.2 交互规则

1. 管理员点击“已预约”单元格时，直接跳转到当前预约信息页面。
2. 管理员点击“待确认”单元格时，直接跳转到当前审核确认页面；`待确认` 在本版本中仅指预约待审。
3. 管理员点击“维护”单元格时，直接跳转到当前维护信息页面。
4. 管理员点击空闲可操作单元格时，不进入预约弹层，而是进入维护创建弹窗或维护创建信息区。
5. 维护创建弹窗标题为“维护仪器”。
6. 维护创建弹窗操作按钮至少包括“取消”和“确认维护”。
7. 管理员可基于当前点击或多选结果直接创建维护时段。

#### 5.9.3 边界

1. 普通用户仍保持预约流程。
2. 管理员维护操作仍需遵守过去时段不可操作和整点规则。
3. 管理员点击非空状态格时，以查看和处理当前状态信息为主，不重复弹出创建维护流程。
4. 管理员点击空闲格时，主语义为创建维护，不再是预约。
5. 管理员状态格跳转优先复用现有页面体系，不新建统一“周历详情页”。

### 5.10 长按防误触优化

#### 5.10.1 目标

避免用户在滑动浏览周历时误触发长按选择。

#### 5.10.2 规则

1. 用户手指发生滑动时，取消长按触发。
2. 只有在稳定按住的情况下，才进入长按选择模式。
3. 不修改现有长按进入选择模式的总体设计。

#### 5.10.3 预期结果

1. 横向或纵向浏览周历时不应误进入选择模式。
2. 正常静止长按仍可触发震动与选择逻辑。

### 5.11 管理首页改造为待办直达

#### 5.11.1 目标

让管理员进入管理页后优先处理待办，不再依赖先进入菜单再定位到处理页面。

#### 5.11.2 首页结构

管理首页拆分为两类区域：

1. 待办直达区
2. 非待办功能区

#### 5.11.3 待办直达区要求

待办项至少包括：

1. 注册用户/课题待审
2. 预约待审
3. 取消待审
4. 隐私请求

每个待办项要求：

1. 显示数量
2. 可点击
3. 点击后直接跳转到对应处理页
4. “注册用户/课题待审”作为统一入口，不再拆成两个独立首页入口
5. “取消待审”同时承接原取消待审与规则复审处理职责

#### 5.11.4 非待办功能区要求

本次保留以下非待办入口：

1. 维护
2. 设置

使用统计并入系统设置，不再单独作为一级入口。

### 5.12 维护逻辑修复

#### 5.13.1 目标

补齐当前维护逻辑中的业务缺口，使前端交互、云函数规则和收敛后的时段治理模型保持一致。

#### 5.12.2 纳入本版本的修复项

1. 创建维护时，只处理未来有效时段；已开始或已结束部分不追溯取消。
2. 创建维护与创建预约之间需要补齐并发保护，避免维护范围内残留新成功预约。
3. 维护管理页与管理列表接口补齐管理员权限边界，避免普通用户读取内部原因或管理数据。
4. 维护覆盖逻辑需要兼容仍在系统中存在的旧结构预约记录，避免遗漏 legacy 数据。
5. 维护创建统一收敛到整点约束，禁止自由文本时间绕开整点业务规则。
6. 下线受限后，预约审核原因与后台待办口径需要同步收敛，去除受限相关分支。

#### 5.12.3 规则要求

1. 维护覆盖应尽量按未来有效时段或未来有效片段处理，不得粗暴取消整张已部分开始的预约单。
2. 管理端列表接口仅服务管理员页面使用，不继续作为公开说明接口。
3. 维护创建必须与周历整点模型一致。
4. 受限下线后，不再保留相关图例、入口、提示文案和审核来源说明。

### 5.13 页面文案与禁用态规范

#### 5.12.1 目标

统一本版本新增交互中的按钮文案、提示文案和禁用态表现，避免不同页面自由发挥造成体验不一致。

#### 5.13.2 周历翻周按钮

1. 正常状态文案保持“上周”“下周”。
2. 多选模式下按钮进入禁用态。
3. 禁用态应同时降低文字和边框强调度，但仍保持可读。
4. 用户点击禁用态按钮时，提示：

```text
多选中不可切换周，请先退出选择
```

#### 5.13.3 维护创建页

1. 页面主操作按钮文案为“新增维护”。
2. 管理员点击空闲格进入维护创建流程时，弹窗标题为“维护仪器”。
3. 周历维护创建弹窗按钮文案为“取消”“确认维护”。
4. 维护页确认弹窗标题为“确认维护”。
5. 维护页确认弹窗主按钮文案为“新增维护”。
6. 确认弹窗中明确出现提示：

```text
将取消未来有效预约
```

7. 无需为维护创建额外设计营销式说明或装饰性副标题。

#### 5.13.4 自动刷新反馈

1. 操作成功后优先使用系统 Toast，文案保持简短。
2. 成功后采用“先提示、后静默刷新”的顺序。
3. 自动刷新过程不额外插入打断式弹窗。
4. 若刷新失败，保留当前页面内容，并提供简短失败提示，不清空已有上下文。

#### 5.13.5 管理首页入口文案

1. 待办卡片标题使用任务导向命名，如“注册用户/课题待审”“预约待审”“取消待审”。
2. 非待办入口仅保留“维护”“设置”。
3. 注册相关入口统一命名为“注册用户/课题待审”。
4. 取消相关入口统一使用“取消待审”，并承接规则复审处理。
5. 使用统计不再作为独立一级入口文案，统一并入“系统设置”。
6. 不保留“注册审核”“课题申请审核”“受限时段”“规则复审”“统计”等已下线或不再作为本版主入口的文案。

#### 5.13.6 禁用态通用要求

1. 禁用态只用于当前上下文不可操作的控件，不替代权限隐藏。
2. 禁用控件保持原尺寸，避免页面跳动。
3. 禁用态必须可区分，但不得使用高风险警告色模拟报错。
4. 禁用态文案不改为模糊表达，如“暂不可用”，应尽量通过上下文说明原因。

## 8. 验收标准

### 8.1 维护时间

1. 管理员无需手动输入完整开始时间和结束时间。
2. 通过日期、开始小时、时长即可完成维护创建。
3. 最终提交结果与现有维护业务逻辑一致。
4. 默认值为今天、下一整点、时长 1 小时。
5. 时长选择范围为 1-12 小时。
6. 确认前可看到起止时间、总时长、受影响预约数量和“将取消未来有效预约”提示。

### 8.2 同课题冲突

1. 同课题成员已占用目标时段时，新预约提交失败。
2. 页面提示为“该时段已被本课题预约”。
3. 普通用户侧不显示具体成员姓名。

### 8.3 预约开放窗口

1. 当前日期可预约到第 7 个自然日的全天整点时段。
2. 示例：当前为周四时，可预约到下周四全天。
3. 不再要求预约单所有时段处于同一自然周。
4. 多选模式本身仍只在当前周内生效。

### 8.4 自动刷新

1. 用户和管理员完成关键操作后，页面自动更新为最新数据。
2. 不需要通过手动刷新才能看到处理结果。
3. 自动刷新不应重置当前周、当前列表位置或当前主要上下文。
4. 成功反馈采用“成功 toast 后静默刷新”。

### 8.5 管理员周历

1. 管理员可在周历中看到“课题简称 + 姓名”。
2. 普通用户不可见姓名。
3. 数据返回路径经过服务端管理员身份校验。

### 8.6 多选与翻周

1. 进入多选模式后，“上周 / 下周”按钮为禁用状态。
2. 退出多选模式后，“上周 / 下周”按钮恢复可用。
3. 多选不能跨周进行。
4. 点击禁用状态的翻周按钮时，提示“多选中不可切换周，请先退出选择”。

### 8.7 长按体验

1. 滑动浏览周历时不会误触发长按。
2. 静止长按时仍可正常进入选择模式。

### 8.8 管理首页

1. 待办数量可点击。
2. 点击后直接进入对应处理页面。
3. 维护、设置仍然可达。
4. 首页只保留一个“注册用户/课题待审”入口。
5. 不再保留“注册审核”“课题申请审核”两个独立管理功能入口。
6. “取消待审”入口同时承接规则复审。
7. 使用统计不再作为独立入口，统一从系统设置进入。

### 8.9 用户管理

1. 用户管理页只显示已通过注册审核的用户。
2. 待审核用户和待审核课题不出现在用户管理页。
3. 已通过但暂停中的用户仍可在用户管理页处理。

### 8.10 受限时段下线

1. 管理后台不再出现受限时段入口。
2. 周历图例和数据接口不再出现受限状态。
3. 受限相关云函数不再由前端调用。
4. 预约审核来源只保留系统规则触发。
5. 当前测试阶段不需要额外保留历史受限数据展示入口。

### 8.11 维护逻辑

1. 维护创建只处理未来有效时段，不追溯已开始或已结束片段。
2. 维护创建与预约创建并发时，不得留下维护范围内仍有效的新预约。
3. 维护相关管理接口完成管理员鉴权与整点约束收口。
4. 管理员点击已预约格时直达预约信息页。
5. 管理员点击待确认格时直达审核确认页。
6. 管理员点击维护格时直达维护信息页。
7. 管理员点击空闲格时进入维护创建流程。
8. 周历维护创建弹窗文案为“维护仪器 / 取消 / 确认维护”。

## 9. 风险与注意事项

### 9.1 隐私风险

管理员周历展示姓名是本版本最敏感的调整点，必须避免以下问题：

1. 在普通接口中默认返回姓名字段。
2. 仅通过前端判断是否隐藏姓名。
3. 在日志中输出姓名或其他敏感信息。

### 9.2 数据口径风险

同课题冲突判断必须与当前有效预约状态保持一致，否则可能出现：

1. 周历看起来已占用，但预约仍可提交
2. 前端显示可预约，但服务端返回同课题冲突
3. 待审核或取消中记录处理口径不统一

### 9.3 预约窗口风险

按自然日开放后，需要同时控制两个边界：

1. 用户可以预约到第 7 个自然日全天
2. 多选过程本身不能跨周

如果前端提示、后端校验和周历交互不同步，用户会感知为“能看到但不能提”或“能提但选不到”。

### 9.4 交互风险

长按防误触优化需要兼顾两类场景：

1. 周历滚动浏览
2. 连续时段选择

如果滑动阈值设置不合理，可能导致长按难以触发或误判率仍然偏高。

### 9.5 首页结构风险

管理首页改为待办优先后，应避免：

1. 只保留待办入口导致非待办功能难以发现
2. 首页数量与实际处理页列表不一致
3. 点击后进入页面仍需二次筛选或再次定位

### 9.6 受限下线风险

受限时段下线后，需要同步清理所有遗留路径，否则会出现规则残留：

1. 周历图例仍显示受限
2. 后台仍保留受限入口但不生效
3. 云函数仍读取 `restricted_slots` 导致用户感知和后台配置不一致

## 10. 建议实施顺序

1. 后端收敛预约规则，完成按自然日开放、同课题冲突与受限下线路径清理。
2. 修复维护逻辑中的取消范围、并发保护、权限边界和整点约束。
3. 改造维护页录入方式并保持接口兼容。
4. 改造周历页与周历组件，补齐管理员展示、多选禁翻周与长按防误触。
5. 改造管理首页待办直达结构。
6. 统一补齐关键操作后的自动刷新。
7. 完成联调与回归验收。
