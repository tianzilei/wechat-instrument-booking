## 1. 目的

本补充计划用于记录 `v0.0.3` 当前实现与原计划之间仍存在的差异，并将差异收敛为可执行补充项。

适用前提：

1. 当前线上/主线版本仍定义为 `v0.0.3`。
2. 原计划中的主链路已基本落地，本文件只补充尚未完全实现的条目。
3. 本文件不扩大业务边界，不引入 `v0.0.4` 或后续版本候选需求。

---

## 2. 当前结论

经对照 `development-plan-v0.0.3.md` 与当前代码实现，`v0.0.3` **尚未完全实现**。

目前确认的缺口集中在以下三类：

1. 管理员周历未真正显示“课题简称 + 姓名”。
2. 已收敛的旧独立页面和旧文案仍有残留。
3. 周历待审状态分流口径与原计划不完全一致。

在此基础上，2026-06-19 已补充确认一组新的 `v0.0.3` 设计收敛项：

1. 周历公开展示从“游客/普通用户统一口径”细化为“游客 / 同课题成员 / 管理员”三级可见规则。
2. “我的”页新增“我的课题”入口，用于查看课题成员和课题内近期预约记录。
3. 运营数据导出改为管理员可导出课题组与预约人信息，并同步补齐隐私政策与导出说明。
4. 底部导航栏选中态、`我的` 与 `管理` 页 dashboard 风格需要补充统一视觉规范。
5. 候补功能仍保留，需补足到现有周历点击后的快捷交互链路。
6. 注册页课题检索已确认同时支持课题全称与课题缩写匹配。

## 3. 差异清单

### 3.1 管理员周历预约人识别未完整落地

原计划要求：

1. 管理员周历单元格展示“课题简称 + 姓名”。
2. 姓名仅在服务端确认管理员身份后返回。

当前情况：

1. `getPublicCalendar` 已区分管理员身份，但返回数据中未附带 `userName`。
2. 周历页 `loadCalendar()` 组装单元格数据时也未写入 `userName`。
3. 周历组件具备显示第二行 `subtext` 的能力，但当前数据无法触发该展示。

结论：

- 该项属于“设计已做到一半，展示未最终打通”，不能视为已完成。

### 3.2 已收敛的旧独立页面和文案仍有残留

原计划要求：

1. 不再保留独立“课题申请审核”入口。
2. 不再保留独立“规则复审”入口。
3. 不再保留独立“使用统计”入口。
4. 文案统一收敛到“注册用户/课题待审”“取消待审”“设置”体系下。

当前情况：

1. `pages/admin/project-review/index`
2. `pages/admin/rule-review/index`
3. `pages/admin/stats/index`

以上页面仍保留在 `app.json` 中，且各自 `navigationBarTitleText` 仍沿用旧命名。

结论：

- 虽然首页导航已按 `v0.0.3` 收敛，但“独立页面仍可访问、旧文案仍存在”的状态，不满足“完全实现”口径。

### 3.3 周历待审状态分流口径偏宽

原计划要求：

1. 管理员点击“待确认”单元格时进入审核确认页。
2. “待确认”在 `v0.0.3` 中仅指预约待审状态。

当前情况：

1. 周历状态映射将 `pending_review`、`cancel_pending`、`rule_review_pending` 都归为待审样式。
2. 管理员点击上述状态时都跳转到 `booking-detail` 的审核模式。

结论：

- 当前实现可以工作，但不完全符合原计划的状态分流定义。

### 3.4 周历公开展示分级口径需要补充

经补充设计确认，周历展示权限不再只有“游客/普通用户”和“管理员”两层，而调整为更接近 Linux 组权限的三层：

1. 游客：只能看到预约所属课题（组）标识，不显示预约人姓名。
2. 相同课题（组）成员：可以在周历格中看到本课题预约人的姓名。
3. 管理员：可以看到全部预约的课题（组）与预约人姓名。

执行口径：

1. 本版本不引入独立于课题之外的新“组”数据模型。
2. “组”在展示与权限层继续等价于“课题”。
3. 此次扩展仅作用于周历格展示，不自动扩展为更多公开详情能力。
4. 服务端必须按当前登录用户的课题归属判定是否返回姓名字段，客户端不得自行推断。

### 3.5 “我的课题”能力当前缺失

经补充设计确认，`我的` 页中的“预约与账号”模块应新增“我的课题”入口。

页面目标：

1. 展示当前用户所属课题（组）的成员列表。
2. 展示课题内成员的预约记录。
3. 展示范围限定为“未来记录 + 最近 7 天内已开启的记录”。

当前情况：

1. `我的` 页目前只有“我的预约”“我的候补”“个人统计”，没有“我的课题”。
2. 现有云函数中没有面向普通课题成员的课题内成员与预约聚合查询接口。

### 3.6 导出字段口径需要扩展

经补充设计确认，运营数据导出仍然只允许管理员执行，但导出内容不再维持当前脱敏口径，而应增加：

1. 课题组信息。
2. 预约人信息。

配套要求：

1. 必须同步更新隐私政策中的导出说明。
2. 必须同步更新后台导出提示文案和说明。
3. 必须明确“该导出仅限管理员使用”的权限边界。

### 3.7 UI 规范需补充

经补充设计确认，当前 UI 还有两类待补规范：

1. 底部导航栏在不同 tab 页面中，应有明确的选中态颜色切换，不应只依赖同一套固定主色。
2. `我的` 与 `管理` 页应采用一致的 dashboard / 卡片结构语言，但通过不同主色区分页面语义。

### 3.8 候补快捷交互链路需补足

经检查，候补功能仍然保留，当前包括：

1. 周历已占用格直接加入候补。
2. 独立“我的候补”页面。

补充设计确认：

1. 候补入口应补到现有周历点击后的快捷交互中。
2. 本次不要求新增完整独立详情页作为唯一入口。
3. 快捷交互中应提供清晰的“加入候补/排队”按钮。

### 3.9 注册课题检索能力已满足，但需写入补充验收

经检查，注册页当前已支持：

1. 课题全称匹配。
2. 课题缩写匹配。
3. 大小写不敏感模糊检索。

结论：

- 此项不属于功能缺失，但应写入补充计划与验收说明，避免后续误判为未支持。
